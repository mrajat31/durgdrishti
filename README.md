# DurgDrishti — Fort & Trail Intelligence

A trail planning and heritage field guide for Maharashtra forts. Crowd, queue, parking, and waste estimates are heuristic planning figures, not live counts or official advisories. Forecast recalculation stays in the browser. The OpenStreetMap basemap and AI photo identification need an internet connection.

The Fort Atlas contains 421 deduplicated name records, combining the app's curated entries with the public [List of forts in Maharashtra](https://en.wikipedia.org/wiki/List_of_forts_in_Maharashtra), the [Forts in Maharashtra category](https://en.wikipedia.org/wiki/Category:Forts_in_Maharashtra), the [Trekshitiz fort directory](https://trekshitiz.com/fort_information.php), and the [UNESCO Maratha Military Landscapes listing](https://whc.unesco.org/en/list/1739/). The Trekshitiz directory includes 335 entries across multiple districts; records explicitly assigned to Goa, Daman, Valsad, or Belgaum were excluded, and overlapping names were normalized before merging. This is a broad discovery index, not an authoritative census: spelling variants may still refer to the same site, and UNESCO's 11 Maharashtra components are selected heritage landmarks rather than a state inventory.

The atlas map shows 323 coordinate-backed OpenStreetMap fort/castle features plus 24 separately mapped catalogue points, for 347 map pins. These are not 347 confirmed unique forts: one fort may have several mapped structures, and some map tags may describe castles or other historic features. Names that match a mapped feature inherit its coordinates; other records open district-aware map searches. The map does not claim 400 mapped forts.

The Fort Explorer combines the statewide map, searchable reference index, and selected-location briefing. Selecting a mapped point updates the briefing and map together. Seven trails have hand-authored planning inputs; they use the existing benchmark-based heuristic. Other mapped points receive explicitly labeled **proxy estimates** from the geographically nearest benchmark when it is within 25 km. For more distant points, the model uses the statewide median of the seven benchmark inputs instead of extrapolating a faraway trail. Proxies are not local measurements and do not verify a site's trail capacity, access, parking, road delay, or waste-disposal capacity; the source and distance are shown. The departure comparison displays alpine, early-morning, and peak windows for the selected point. Map pins remain map features, not a count of unique forts. Fort histories are shown only when an exact Wikipedia article match is found, with a source link. Verify trail access and current conditions locally. The photo finder includes clearly labeled Rajgad and Kalsubai sample assessments to demonstrate the AI result format; these examples are not generated by the model.

Every mapped briefing includes a trek checklist, route-directory/map searches, nearby-service searches, and local-access verification links. Route listings and service searches are third-party results, not verified or endorsed recommendations. The selected location also loads a seven-day regional weather forecast from [Open-Meteo](https://open-meteo.com/) and searches [Wikimedia Commons](https://commons.wikimedia.org/) for a matching free-license photo; image results include artist/source and license links when available. Photos may be unavailable for some pins, and matching search results are not an official site survey. Weather is model data, not a fort-top observation or safety warning. Live weather and image lookup require an internet connection.

## Run locally

```powershell
npm.cmd install
npm.cmd run dev
```

The commands use `npm.cmd` for Windows PowerShell; on macOS or Linux, use `npm` instead.

Run the unit checks and the linter, and create a production bundle:

```powershell
npm.cmd test
npm.cmd run lint
npm.cmd run build
npm.cmd run preview
```

ESLint checks the code for common mistakes, including React hook rules (`eslint.config.js`).

The client bundle is written to `dist/`. No database or user authentication is needed. The optional AI photo feature uses the serverless function in `api/identify.js`; `npm run preview` serves only static files and does not emulate that function.

## Deployment

- **GitHub Pages:** every push to `main` builds and publishes the static app through `.github/workflows/deploy-pages.yml`. In the repository's Settings → Pages, set the build and deployment source to **GitHub Actions**. The app will be available at `https://mrajat31.github.io/durgdrishti/`. GitHub Pages does not run `api/identify.js`, so photo analysis requires a serverless host such as Vercel; the rest of the app remains available.
- **Vercel (recommended for AI):** import the repository and add `OPENAI_API_KEY` under Project Settings → Environment Variables. Vercel serves `api/identify.js` as a serverless function alongside the Vite site. The API key must be configured as a secret; do not put it in `VITE_*` variables.
- **Netlify:** the static atlas and forecasting UI can be published from `dist`, but `/api/identify` will not exist without a serverless-function adapter.

## AI photo identification

The Fort-or-Peak Finder sends a resized photo to OpenAI's `gpt-4o-mini` vision model through the server-side `api/identify.js` endpoint. The OpenAI key is never sent to the browser. Copy `.env.example` to `.env`, add your key, and restart the dev server to use the local API. In production, set `OPENAI_API_KEY` in Vercel Project Settings → Environment Variables. Configure an OpenAI project budget; the endpoint limits request image size and applies best-effort per-instance rate limiting.

The user is told before analysis that the photo is sent to OpenAI. This site does not store the image. Review OpenAI's applicable API data policies and privacy terms before deployment. AI results are visual suggestions, not authoritative heritage or safety assessments.

The Fort Atlas aggregates public indexes, not a complete official Maharashtra fort register. Coordinates are plotted only when available from the source/reference data. Forecasts for the seven benchmarked trails use hand-authored inputs; forecasts for other mapped points are clearly identified as nearest-benchmark proxies, not site-specific measurements.

The Leaflet map's OpenStreetMap raster tiles, AI photo analysis, and outbound map directions require a network connection. Forecast recalculations run locally in the browser.

## Personalized discovery and contributions

On a first visit, people can optionally save a name, age range, completed-trek count, previously visited forts, and trip interests. This profile stays in that browser's local storage; it is not uploaded or attached to a contribution. The age range is not used to rate a route or assess safety. The profile can be skipped, edited, or cleared from the home screen.

Recommendations use the saved interests, de-prioritize previously visited forts, and prioritize the seven forts with coordinates, a fort-specific description, and hand-authored planning inputs. Trek count is shown as context, not a difficulty rating. Interest matching is limited to features supported by those descriptions; interests without reliable fort-specific data are called out rather than guessed. This is a starting point, not a difficulty or safety recommendation.

The dashboard summarizes district labels in the index and compares modelled crowd-pressure estimates for the seven benchmark forts. District totals count index records (not unique, officially verified forts), and hotspot values are not live visitor counts or current trail conditions.

Fort profiles with missing data include a prefilled link to create a public GitHub issue. Contributors should provide reliable source links and avoid personal or sensitive information. There is no in-app contribution backend or private submission channel.
